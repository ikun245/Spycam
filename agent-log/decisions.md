## D-1 前端构建的 esbuild 临时目录问题（环境决策）

- **日期**：2026-10-29
- **现象**：`npm run build` 在 transform 完成后的 transpile 阶段稳定报 `Access is denied`（esbuild 清理系统 TEMP 下的临时文件失败），两次复现，非偶发
- **AI 建议**：无（AI 未预见；属于本机环境与杀软实时扫描的相互作用）
- **判断**：TypeScript 编译（tsc -b）已通过、3072 模块 transform 完成，问题只在 esbuild 与系统 TEMP 交互；把 `TMP/TEMP` 重定向到项目内目录即可绕过，无需改动代码或依赖版本
- **结果**：设置 `$env:TEMP=$env:TMP=<项目>\.tmp` 后构建成功（1.03MB 主 chunk，gzip 325KB）；`.tmp` 已加入 .gitignore
- **教训**：Windows 上构建工具链的临时文件行为受杀软影响，先重定向 TEMP 再考虑换工具版本

## D-3 P0 卡点分层：控制通道假故障 vs 数据面未实现

- **日期**：2026-10-29
- **现象**：`suricatasc` 长时间无响应，容易误判为 Suricata unix-socket 不兼容。
- **备选原因**：a) socket 路径/参数错；b) Suricata 不接受控制命令；c) `/readyz` 的状态探针留下空闲连接；d) 回放 API 和 worker 尚未实现。
- **验证过程**：确认参数格式为 `suricatasc -c uptime /var/run/suricata.socket`；重启清空旧连接后命令返回 `OK`；修复探针后连续 5 次 `/readyz` 均 200，`uptime` 仍成功；`pcap-file` 命令清楚返回 filename 不存在，确认控制命令工作。另一方面，真实 `POST /api/v1/replay-tasks` 返回 501，worker 代码只连 PG/Redis 后等待信号。
- **判断与结论**：c 是造成控制通道排查卡住的真实 bug，已修复；d 才是当前“无法验收 P0 闭环”的根因。P0 不能因为服务健康或引擎可控就宣称完成。
- **后续**：实现上传与回放任务 API、worker 队列消费、eve 解析入库，再用真实 pcap 验收。

## D-5 产品化转向：竞品调研驱动的功能补齐

- **日期**：2026-10-29
- **背景**：用户批评系统"为了完成而完成"——规则只能启停不能创建（新攻击手法=改代码）、总览图表永远空、界面全英文，要求调研安全厂商产品
- **调研对象**：Scirius（Suricata 官方规则管理：UI 建规则/抑制/阈值）、SafeLine 雷池（本机有源码：`getAttackType` 中文映射、检测日志字段即界面文案）、Security Onion（Detections 统一管理）
- **AI 建议**：补"规则可视化生成器"（这是需求 C2 加分项的表述）
- **实际选择**：不做可视化生成器，做**结构化表单创建规则**（协议/方向/五元组/内容/阈值/阶段/等级）——表单覆盖高频场景且实现可靠，可视化编辑器 48h 内做不完整
- **结果**：浏览器内创建"8443 端口管理后台爆破检测"实测热加载生效；总览修复时间过滤 bug 后图表有真实数据；界面全面中文化（高危/中危/低危、侦察/爆破/利用/C2/外泄）
- **教训**：加分项的表述（"可视化生成器"）不等于用户价值（"新手法无需改代码"）；**从运营场景倒推功能形态**，而不是照需求字面实现

## D-7 Docker 不可用时手写 sqlc 生成代码

- **日期**：2026-10-30
- **背景**：告警列表过滤/排序、审计、stats 新列都要改 sqlc 查询；宿主 Docker Desktop 未运行，下载的 sqlc Windows 二进制缺 MinGW DLL（0xC0000135），32 位 Go 编译 sqlc 过慢
- **备选**：A. 绕过 sqlc，在 handler 里直接写 pgx 查询；B. 等 Docker；C. 按 sqlc 1.27 输出格式手写生成代码，事后用容器生成比对
- **实际选择**：C。保持“SQL 只在 `queries/*.sql`、全部参数绑定”的约束不破例；手写代码严格模仿生成格式（参数按首次出现编号、timestamptz→`pgtype.Timestamptz`、可空 uuid→`*string`）
- **风险与补救**：手写可能与真实生成有细微差异（字段顺序/注释），已写入 AGENTS.md：Docker 可用后执行 `sqlc generate` 并 `git diff` 比对
- **教训**：工具不可用时守住的是**约束**（参数绑定、单一 SQL 来源），而不是工具本身

## D-8 实时推送粒度：任务事件而非逐条告警

- **日期**：2026-10-30
- **背景**：C1 要接通 SSE；架构设计原意是逐条告警推送
- **事实**：离线回放模式下，worker 在 Suricata 处理完整个 pcap 后才批量采集入库，不存在“告警逐条到达”的时刻；逐条 PUBLISH 上千条告警只会让前端重复刷新
- **实际选择**：按任务生命周期推送（running/done/failed，done 携带新增告警数与事件数），前端收到后让列表查询失效重拉并弹通知；轮询保留为降级
- **教训**：实时推送的粒度应跟随**数据实际产生的节奏**，而不是照搬“告警推送”的字面

## D-9 规则校验前移：写库前先 `suricata -T -S 候选文件`

- **日期**：2026-10-30
- **背景**：`POST /v1/validate-rules` 一直是 501 占位，新建规则只能“先写库 + 生成文件 + 重载，失败再回滚”（Bug-15 就出在回滚不对称）
- **备选方案**：a) 继续靠回滚兜底；b) agent 提供独立校验端点，api 在写库前调用
- **实际选择**：b。agent 把候选规则写入临时目录，用参数数组执行 `suricata -T -c suricata.yaml -S <tmp>/candidate.rules -l <tmp>`：`-S` 只加载该文件，不触碰运行中的规则集；请求体限 256KiB，临时目录用后删除，返回的错误详情剥离临时路径、只取最后一行。重载链路的回滚保留为第二道防线
- **未验证**：本机 Docker 未运行，`-S` 与 `-T` 组合在 jasonish/suricata 镜像内的实际输出尚未实测；agent 侧仅有输入校验的单测
- **教训**：能在副作用之前做的校验就不要放到副作用之后用回滚补

## D-10 C1 实时抓包：独立 af-packet 引擎实例 + 尾随采集

- **日期**：2026-10-30
- **背景**：对照题面复核时发现系统只有离线回放链路；C1 要求“实时抓包 + 推送”
- **备选方案**：a) 复用 unix-socket 引擎（该模式只支持 pcap-file，不行）；b) 定时 tcpdump 切片后走回放队列（延迟取决于切片周期，且重复落盘）；c) 独立 Suricata 实例 `--af-packet`，worker 尾随 eve.json
- **实际选择**：c，放在 compose `live` profile，默认不启动。
  - 引擎：`network_mode` 默认 host，接口与 HOME_NET 走环境变量并做字符白名单。容器内 watcher 监测 rules-active 的校验和，变化时发 USR2 热重载，因此无需挂 docker.sock
  - 采集：worker 每秒从 Redis 记录的偏移继续读，只消费完整行；文件变短时偏移归零
  - 数据模型：按接口生成确定性 UUID 的 pcap/task（sample_type=live），复用全部告警、聚合、事件表和去重键
  - 推送：SSE 消息 `type:"live"`
  - 不支持的操作：取证切片与“重放”对 live 源返回 409，因为没有落盘 pcap
- **实测**：bridge 模式 DNS 隧道告警，包→入库 0.16–0.30s；host 模式下真实 HTTP 外联触发 C2 心跳规则（sid 1000006），延迟 0.46s；规则禁用后 live 引擎热重载，告警停止
- **局限**：Docker Desktop 的 host 网络是 VM 网卡，看不到 Windows 局域网流量；真实网卡需 Linux 主机，或用 SPAN/镜像口、远程 tcpdump 转发；live eve.json 不轮转
- **教训**：实时与离线差别在数据入口，下游模型应保持同一套，否则聚合、事件、处置都要做两遍

## D-11 已知缺陷收口：轮转按 inode、stats 按来源拆分、锁定按用户名+IP

- **日期**：2026-10-30
- **背景**：README“已知缺陷”列了 7 条，用户问“缺陷能修复吗”。逐条评估后修 6 条；实时源取证留作声明：题面排除全量包存储，环形 pcap 落盘的磁盘与隐私成本要部署方另行评估
- **决策**：
  - eve 轮转：容器内 watcher 在超过 `LIVE_EVE_MAX_MB` 时 `mv eve.json eve.json.1` 并 SIGHUP。worker 游标从“偏移”改为“inode:偏移”。inode 变化时先把 `.1` 从旧偏移读完再从新文件 0 开始，因此轮转不丢行。旧游标（纯数字）兼容解析。选它而不用 copytruncate，是因为后者在拷贝与截断之间写入的行会丢
  - stats 拆分：`engine_stats` 加 `source` 列，主键改为 `(source, ts)`。回放 stats 的 ts 是 pcap 时间，实时是墙钟，不分来源时“最新一条”永远是实时实例
  - 登录锁定：键从“用户名”改为“用户名+clientIP”（5 次）。另加用户名总计 50 次的上限，防分布式爆破。以前任何人从任意 IP 都能把 admin 锁 15 分钟
  - Cookie：`COOKIE_SECURE` 环境变量，默认 false（本地 http），HTTPS 反代部署时开启；登出清 Cookie 时属性与登录一致
  - 依赖：用 Docker 内 govulncheck 补跑扫描，结果见 Bug-25
  - 部署：全部常驻服务 `restart: unless-stopped`，Linux 上 Docker 开机自启即整套恢复
- **自验指标**：§5.4 要求的告警延迟与去重率补进报告。延迟拆成两项：检测延迟（pcap 时间，GT 窗口起点→首条命中告警）衡量规则灵敏度；管道延迟（墙钟，任务创建→入库）衡量系统吞吐。两者混在一起没有意义

## D-12：回放从常驻 unix-socket `pcap-file` 改为每任务独立 `suricata -r`

- **日期**：2026-10-30
- **背景**：Bug-26，常驻实例跨任务保留 host/阈值状态，同一 pcap 重放结果不稳定
- **备选方案**：
  - a) 每个任务前重启常驻实例：需要信号或进程管理，规则热重载窗口会被打断
  - b) 给场景分不同源 IP 规避：只是绕开验证，真实用户重放仍不一致
  - c) agent 串行为每个任务起独立的 `suricata -r` 进程
- **AI 的建议**：最初写进自验报告的是 b
- **实际选择**：c。架构设计 §13 早就把这条列为预案。参数数组固定、关闭 unix-command、5 分钟超时，满足 M7。启动开销约 0.5s，对离线回放可以忽略。常驻实例保留，负责规则 `-T` 校验后的热重载和状态展示。worker 协议不变，只新增 `errors[task_id]` 回传失败原因
- **代价**：失去“热重载即对下一个回放生效”的进程复用，但每个任务都从 rules-active 读规则，效果相同

## D-13：web 发布地址改为 `WEB_BIND`/`WEB_PORT` 可配置，默认仍为回环

- **日期**：2026-10-30
- **背景**：Linux 服务器部署后公网无法登录，用户担心 `8080:80` 与宿主机 nginx 抢端口。实际 `:80` 是容器内端口，不占宿主机端口。打不开的原因是端口硬编码绑定 `127.0.0.1`
- **备选方案**：
  - a) 直接改成 `0.0.0.0:8080`：开箱可访问，但会默认暴露明文 HTTP 登录口
  - b) 地址和端口走环境变量，默认 `127.0.0.1:8080`，README 给出宿主机 nginx HTTPS 反代示例和直接暴露的测试方式
- **实际选择**：b。默认值仍满足 M7“仅 web 对外、最小暴露”。按用户要求“禁止使用 80、8080”，宿主机默认端口和容器内 nginx 监听端口都改为 28765。端口冲突时只需修改 `WEB_PORT`
- **代价**：公网访问需要多配一层反代或手动改 `.env`；经宿主机反代时，登录锁定的 IP 维度仍会退化（见 README 已知缺陷）

## D-14：实时抓包改为常驻服务，网卡自动探测，界面不放操作说明

- **日期**：2026-10-30
- **背景**：Linux 部署后用户按 `docker compose up -d` 启动，`suricata-live` 属于 `live` profile 未被启动，界面也没有任何提示，看起来系统一直是离线的。另外 `LIVE_IFACE` 默认 `eth0`，云主机常见网卡名为 `ens3`/`enp0s3`，即使启动也会因网卡不存在而退出
- **备选方案**：
  - a) Web 提供“启动实时抓包/选择网卡”按钮：需要 api 挂载 docker.sock 或拥有宿主机网卡权限，违反 M7 红线
  - b) 在引擎状态页写接入指南（第一版做法）：用户否决，产品界面不应承载部署说明，说明应写在文档里
  - c) `.env` 中设置 `COMPOSE_PROFILES=live`：仍依赖用户记得改配置，旧 `.env` 不会生效
  - d) 去掉 profile，实时抓包作为常驻服务写死；`LIVE_IFACE` 为空或网卡不存在时回退到默认路由网卡
- **实际选择**：d。entrypoint 把实际网卡写入 `eve-out/live/iface`，worker 以此命名实时数据源；引擎状态页只显示状态与统计。部署说明保留在 README，另提供只读诊断脚本 `scripts/server-check.sh`，用户在服务器运行后回传结果。`suricata.yaml` 显式开启 VXLAN/Geneve 解封装，以接入云流量镜像
- **代价**：Windows/macOS 本机演示也会启动实时容器（只能看到 Docker VM 自身流量，资源占用小）；不能在 Web 上启停或切换网卡；只输出 syslog 的安全产品没有原始流量，仍不能接入
