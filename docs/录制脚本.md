# D3 录制脚本：5–8 分钟演示（逐句台词 + 操作）

> 要求（需求梳理 §3 D3）：**不剪辑**，从空环境启动 → 回放 pcap → 界面出告警 → 展示自验报告。
> 本脚本按 6 分 30 秒设计（含缓冲）。**录制前先完整走一遍排练**，确认每条命令都能跑。
> 录制工具建议：OBS Studio / Win+G，录全屏 + 麦克风。**一个镜头到底，不剪辑。**

- [ ] 检查麦克风；语速：正常说话，不赶

## 第 0 段（0:00–0:30）开场 + 空环境声明

**操作**：切到终端，执行并停顿展示：

```powershell
docker compose ps
```

预期输出：空列表（或 no services 运行）。

**台词**：
> 大家好，这是 Spycam 流量威胁检测系统的完整演示。当前是一个干净的空环境——没有任何容器在运行，数据库也是空的。接下来我会从零启动整个系统，演示从流量回放到告警研判的完整链路，最后展示数据自验报告。

---

## 第 1 段（0:30–1:30）一键启动

**操作**：

```powershell
Copy-Item .env.example .env -Force
docker compose up -d
```

**台词**：
> 整个系统用 docker compose 一键启动，一共六个服务：nginx 入口、Go 语言的 API 和 worker、Suricata 检测引擎、PostgreSQL 和 Redis。数据库密码、引擎通信 token 全部通过环境变量注入，仓库里只有点 env example 模板，密钥不进代码库。

**操作**：等约 20–30 秒，期间继续说（不要冷场）：

```powershell
docker compose ps
```

**台词**（等容器时说）：
> 启动过程中 API 会自动做三件事：执行数据库迁移建表、导入内置检测规则、种子化初始管理员账号。所以不需要任何手工配置步骤，干净机器十五分钟内一定能跑起来——这里因为镜像已经构建好，实际只要三十秒。

**验收点**：六个服务全部 `Up`/`healthy` 再进下一段。

---

## 第 2 段（1:30–2:15）架构一页讲清

**操作**：切到 README.md 的架构图部分，滚动展示。

**台词**：
> 先用三十秒说下架构。流量从 pcap 文件回放给 Suricata 引擎，每个回放任务由 agent 启动一个独立的 Suricata 进程，任务之间状态互不污染，产出的 eve.json 由 worker 采集归一化后写入 PostgreSQL；Redis 负责任务队列、事件流和实时推送。前端只通过 API 访问数据，完全不接触引擎——这是标准的分层隔离。有两个安全设计点：第一，所有服务里只有 nginx 对外暴露一个端口，其余全在内部网络；第二，操作引擎走的是一个带 token 鉴权的内部 agent，全系统没有任何地方挂载 docker.sock。

---

## 第 3 段（2:15–3:00）登录 + 总览

**操作**：打开浏览器 → `http://127.0.0.1:8080` → 登录页输入 admin / 你设定的密码 → 进入总览页。

**台词**：
> 打开浏览器访问本机 8080 端口。系统有登录和角色控制，分只读、分析员、管理员三级。登录进来是总览页——当前告警是零，因为数据库刚初始化，接下来我们造真实告警。总览页包含告警时间分布、威胁等级分布、攻击来源排行、命中规则排行，数据全部来自数据库实时统计。

---

## 第 4 段（3:00–4:15）回放 pcap → 实时出告警（核心段）

**操作**：
1. 侧栏点「数据与回放」
2. 拖入 `scan_syn.pcap`（或点选择文件）
3. 等任务状态变 `done`（约 5–10 秒，期间解说）

**台词**（上传时）：
> 现在回放第一个 pcap——这是一次分布式端口扫描：三个外网攻击源，分别扫描三台内网服务器的低端口。上传后系统自动创建回放任务，入队交给 worker 处理。

**台词**（任务 done 后）：
> 任务几秒内完成：Suricata 引擎检测出 234 条告警。注意整个链路是自动的：agent 收到回放指令后为该任务启动独立的 Suricata 进程，eve.json 由 worker 采集归一化入库，同时通过消息推送实时通知前端。

**操作**：切到「告警列表」页，滚动展示几行，点开任意一条进详情。

**台词**：
> 告警列表能看到时间、五元组、签名、威胁等级。点开任意一条看详情：完整的规则原文、命中的 payload 内容、关联的流统计、还有原始 JSON——所有来自流量的数据都只做文本渲染，从根上防 XSS。页面里也能直接把这条告警对应的原始 pcap 导出做取证。

---

## 第 5 段（4:15–5:15）多源数据 + 聚合 + 事件串联

**操作**：
1. 回「数据与回放」，再上传 `web_attacks.pcap`（Web 攻击：SQLi + XSS，三个源打三台资产）
2. 等 done，切「总览」页展示图表变化
3. 切「攻击事件」页，点击事件行展开攻击链

**台词**（上传第二个 pcap 时）：
> 再回放一个 Web 攻击场景：三个攻击源对三台 Web 服务器做 SQL 注入和 XSS。这个 pcap 有一千多包、两百多个完整 HTTP 会话。

**台词**（总览页）：
> 回到总览——告警总数涨到四千多，时间分布图出现了两个明显的攻击时间窗，攻击来源排行里有五个不同的外网 IP，还有内网失陷终端——10.0.0.100，它就是后面 DNS 隧道和 C2 心跳的源头。攻击类型分布在漏洞利用、侦察、命令控制、暴力破解四个阶段。

**台词**（攻击事件页）：
> 这是事件串联：同一攻击源的告警会按时间归并成攻击事件，并且带攻击阶段标注——侦察、爆破、利用、命令控制——阶段信息来自规则里的 ATT&CK 元数据。一个真实攻防场景里，分析员看这一页就能知道对方打到了哪一步。

---

## 第 6 段（5:15–6:15）规则热更新（产品能力核心段）

**操作**：
1. 切「规则管理」页，展示规则列表（内置 6 条 + 阶段/ATT&CK 标签）
2. 点「新建自定义规则」，边填边说：
   - 协议 TCP、方向 源→目的
   - 源 any、目的 `$HOME_NET`、端口 `5985`
   - 描述输入：`检测到 PowerShell 远程管理爆破`
   - 阶段选「暴力破解」、等级选「高危」
   - 频次阈值 15 次 / 30 秒
3. 点「创建并热加载生效」，等成功提示
4. （可选加分）切回终端执行：

```powershell
docker compose exec suricata grep 2000001 /opt/spycam/rules-active/spycam.rules
```

**台词**（填表时）：
> 重点来了——真实运营里最难的问题：今天出现了一种新的攻击手法，系统怎么办？传统的做法是改规则文件、重新打包、重启引擎。在这里，分析员直接在界面上新建规则。我选协议、填方向和端口、写中文描述、指定攻击阶段和威胁等级，再配一个频次阈值。

**台词**（提交后）：
> 点创建，规则立即写入库、生成规则文件、通过 Suricata 的语法校验、然后热加载——**不需要重启引擎，也不需要改任何代码**。我们到容器里验证一下，新规则 sid 2000001 已经真实写进了引擎正在使用的规则文件。如果规则语法有问题，系统会自动回滚并报错，不会让引擎加载坏规则。

---

## 第 7 段（6:15–7:00）自验报告收尾

**操作**：
1. 切终端，执行：

```powershell
docker compose --profile tools run --rm validator
```

2. 等评测跑完（约 1–2 分钟，会逐场景打印），期间解说
3. 展示输出后，用编辑器/浏览器打开 `validation/out/report.md`

**台词**（评测跑时）：
> 最后是这道题最核心的部分——自证检测有效性。自验评测是一条命令：它自己登录系统、把六个场景的 pcap 逐个回放、通过公开 API 拉取原始告警、和事先写好的 ground truth 逐条比对，算出每个场景的准确率和召回率。注意评测程序是一个黑盒，它只走产品 API，不碰数据库——验证的就是真实产品路径。

**台词**（展示 report.md）：
> 结果：六个场景全部检出，总体精确率 1.0、召回率 1.0，误报为零——包括三千多包的正常业务流量，没有触发任何规则。变异测试三个变种，预判全部命中。报告里也如实写了未解决问题：比如取证导出还没做时间切片、规则外的新手法要靠界面建规则来覆盖。完整的报告和评测数据都在仓库的 validation 目录下。

---

## 第 8 段（7:00–7:20）收尾

**操作**：切回浏览器总览页，停留 3 秒。

**台词**：
> 总结一下：这是一套从流量到告警到研判的完整闭环——一键部署、规则热更新、事件串联、实时推送，并且用自建数据和 ground truth 证明了检测有效性。谢谢观看。

（结束录制）

## 常见翻车点与预案

| 风险 | 预案 |
|---|---|
| 容器启动慢 | 第 1 段的解说词就是为等待期设计的；若超过 60 秒，切 README 讲架构消化时间 |
| 评测命令卡住 | `validator` 依赖 api 就绪——确认第 4 段登录成功过再跑；卡住就等（有 120s 超时自动结束） |
| 登录密码错误 | 用 .env 里 `SEED_ADMIN_PASSWORD` 的实际值；录制前先手动登一次确认 |
| 说错话 | **不要停**，直接说"更正一下"重说一遍；不剪辑 |
| 任务一直 running | 终端另开 `docker compose logs worker --tail 5` 看进度，解说"worker 正在采集 eve 日志" |
