# 流量威胁检测系统动手考题：需求梳理

> 本文依据 [考生题面.docx](考生题面.docx) 整理，方便快速拆解实施与验收；原题面仍是完整要求的最终依据。未完成项、误报和已知缺陷必须如实记录，不得伪造数据或结论。

## 1. 题目概览

| 项目 | 要求 |
|---|---|
| 招聘岗位 | 网络安全产品研发（应届），计划录用 5 人 |
| 形式与时限 | 个人限时动手题，48 小时；建议实际投入不超过 20 小时，并记录工时 |
| 核心目标 | 基于 **Suricata** 构建带 Web 界面的流量威胁检测系统，并用自建数据证明检测效果 |
| 架构 | B/S 架构；前端经后端 API 读取数据，不直接访问 Suricata |
| 技术选择 | **Suricata** + 自选后端、前端、数据库；优先容器化 |
| 工具政策 | 可使用任意 AI 编程工具和开源组件；必须能解释提交的代码 |
| 总分 | 作品 100 分，额外加分最多 10 分；另有现场答辩与盲测 |
| 截止时间 | 以招聘邮件通知为准；迟交每小时扣 5 分，超过 6 小时不收 |

## 2. 要解决的问题

把 pcap 或可选的网卡流量交给 **Suricata** 检测，将告警及流量元数据采集、归一化并写入数据库，再通过后端 API 提供给 Web 界面，支持分析员查看和研判。

```text
pcap / 网卡 → Suricata（IDS）→ eve.json → 采集器 → 数据库 → 后端 API → Web 界面
```

最低要求是浏览器中能看到数据并执行操作。只有 CLI、JSON 文件或 **Kibana** 截图不构成完整交付；界面与核心业务逻辑必须自建。

## 3. 必须提交的交付物

| 编号 | 交付物 | 验收重点 |
|---|---|---|
| D1 | Git 代码仓库，提供链接或 zip | 保留完整 commit 历史；跨两天至少 10 次提交 |
| D2 | 一键启动方式 | `docker compose up` 或等价方式；干净机器在 15 分钟内启动 |
| D3 | 5–8 分钟录屏 | 不剪辑；从空环境启动、回放 pcap、界面出现告警，到展示自验报告 |
| D4 | 一页纸自验报告 | 列明场景、期望、实际、TP/FP/FN、误报归因和未解决问题 |
| D5 | `agent-log/` | 记录关键 Agent 交互、决策、错误及代码审查过程，详见第 7 节 |

建议仓库至少包含：README（架构图、启动步骤、设计取舍、已知缺陷）、容器配置、规则、后端、前端、自建数据及生成脚本、ground truth、自验脚本与报告、`agent-log/` 和自验说明文档。

## 4. 功能范围（MoSCoW）

### 4.1 Must：必须实现

| 编号 | 要求 | 验收方式 |
|---|---|---|
| M1 | pcap 流量回放给 **Suricata**；在线网卡抓包可选 | 给定新 pcap 后能够产生检测结果 |
| M2 | **Suricata** 以 IDS 模式运行，加载仓库内自定义规则并输出 `eve.json` | `suricata -T` 校验通过，规则文件可检查 |
| M3 | 消费并归一化 `eve.json` 中的 alert、flow、dns、http、tls 事件并落库 | 数据库可查到结构化记录 |
| M4 | 提供完整 Web 界面，具体要求见下表 | 现场操作演示 |
| M5 | 至少 4 类攻击场景和 1 类正常负样本；自动计算 TP/FP/FN | `make validate` 一条命令生成报告 |
| M6 | 干净环境一键启动，镜像和依赖版本锁定 | 面试官自行运行验证 |
| M7 | 做好系统自身安全，具体要求见 4.4 | 现场 payload 安全测试 |

M4 界面必须同时包含：

- **告警列表**：时间、五元组、签名、severity、协议、处置状态；支持过滤、排序、分页。
- **告警详情**：签名全文、规则原文、原始 JSON、关联 flow、payload 摘录。
- **总览**：时间趋势、Top 源 IP、Top 签名、Top 目的端口。
- **规则管理**：查看、启停；更改后必须确实影响检测。

### 4.2 Should：建议实现

- **S1 告警聚合/抑制**：同签名、同五元组在可配置的 N 秒内聚合，并显示命中计数；不得把多阶段攻击合并丢失。
- **S2 处置流转**：支持“新 → 已确认 / 误报 / 忽略”，记录操作人和时间，可审计。
- **S3 事件串联**：按同一源 IP 和时间把多条告警串成攻击事件，并体现扫描、爆破、入侵等阶段。
- **S4 告警取证**：可按时间戳和五元组定位原始 pcap 片段并导出。
- **S5 登录与角色**：至少提供只读、分析员两种角色。
- **S6 引擎可观测**：展示 **Suricata** 运行状态、规则加载耗时、丢包计数和告警吞吐。

### 4.3 Could：加分项（合计最多 +10）

- **C1** 在线抓包及 SSE / WebSocket 实时推送。
- **C2** 规则可视化生成器，或支持阈值、频次、时序等自定义检测逻辑。
- **C3** 告警映射到 MITRE ATT&CK 技术，并在界面呈现攻击链。
- **C4** 用 LLM 研判或降噪，并提供准确率及幻觉案例评测；没有评测不加分，反而可能扣分。
- **C5** 多任务或多 pcap 并发回放，并隔离各任务结果。

### 4.4 系统自身安全（M7）

- pcap 文件名和规则内容不得引发命令注入或路径穿越。
- 前端必须转义告警 payload，防止 XSS；例如含 `<img src=x onerror=alert(1)>` 的 payload 不应执行。
- 数据库密码和 API Key 不得硬编码；通过 `.env` 等外部配置提供，且 `.env` 不提交到 Git。
- 提交 `pip-audit` 或 `npm audit` 结果，并说明如何处理依赖问题。
- 现场会测试相关 payload；不要求绝对无漏洞，但必须知道并说明未防住的地方。

## 5. 数据自验（核心考察项）

### 5.1 自建数据集

不得只下载公开 pcap 后截图交差。使用 **Scapy**、自写脚本或 **tcpreplay** 等构造数据：

- 至少 4 类攻击，每类至少 1 个 pcap。可选：端口扫描（SYN/FIN/XMAS）、SSH/FTP/HTTP 表单暴力破解、Web 攻击（SQLi/XSS/命令注入/路径穿越）、DNS 隧道或异常 DNS、C2 心跳、TLS 异常、数据外泄、SMB/RDP 横向爆破等。
- 至少 1 类正常流量作为负样本，混合 HTTP/DNS/TLS，包数应足够，不能只有十几个包。
- 每个 pcap 建议 1,000–50,000 个包；太大影响运行，太小缺少统计意义。

### 5.2 Ground truth 先于检测

每个 pcap 都要有对应的 `ground_truth.json`，先写预期，再运行检测。每条期望至少说明：

- 期望命中的 sid、源/目的 IP、目的端口范围和协议。
- 期望告警的开始、结束时间窗，不能只写“整段 pcap 曾出现”。
- pcap 是否为负样本、场景描述及已知限制。
- 可选的 `min_count` 等用于表达预期命中次数的字段。

### 5.3 自动评测与判定口径

一条命令完成环境启动、全部 pcap 回放、告警采集、与 ground truth 比对，并输出机器可读 `report.json` 和人读 `report.md`。

- **TP**：至少一条告警同时满足 sid 匹配、五元组匹配（目的端口在范围内）且时间落入预期窗口。
- **FN**：某场景中的每条预期都没有命中。
- **FP**：负样本 pcap 的任意告警；或攻击 pcap 中五元组、时间窗完全不匹配的告警。
- 如采用不同判定口径，必须在报告中写清楚，以便复算。

### 5.4 报告指标

- 每个场景分别给出 Precision、Recall、F1，不可只提供总分。
- 总体 Precision、Recall 按告警条数计算，并说明具体口径。
- 告警时延：从首个攻击包时间戳到告警入库时间，给出均值和最大值。
- 去重率：对比原始告警条数和聚合后条数。
- 误报明细：负样本产生的每条告警都要逐条解释原因和处理方式。

### 5.5 变异测试、盲测与诚实性

- 至少对 2 个场景做变种并解释检出率变化。变种可包括更换源/目的端口、改变 payload 编码/大小写/空格/URL 编码、分片、拆成多次小请求或加入延时（如快扫改慢扫）。重点是预判规则会不会失效、失效原因是什么。
- 答辩盲测会提供未见过的 pcap，要求在 3 分钟内运行并解释检出、漏检及原因。
- 报告必须列出 FN 和已知缺陷。结果全绿会被复核；伪造数据或结果将直接淘汰。

## 6. Agent 使用记录（`agent-log/`）

记录重点是如何指挥 Agent、验证产出和承担工程判断，而不是模型或 token 数量。

| 文件 | 最低要求 |
|---|---|
| `prompts.md` | 至少 10 条关键 prompt；按“目标 + 约束 + 验收标准”记录，并标注有效或无效 |
| `decisions.md` | 至少 5 个关键决策；记录备选方案、AI 建议、自己的判断和结果 |
| `bugs.md` | 至少 3 个 AI 引入的错误；说明如何发现、验证和修复，例如幻觉 API、错字段、错 SQL、安全漏洞或编造配置项 |
| `review.md` | 审查清单至少覆盖输入校验、SQL 注入、命令注入、路径穿越、密钥硬编码和依赖漏洞 |

> ⚠️ `bugs.md` 为空或声称“AI 生成代码没有 bug”属于红旗；应记录真实发现和验证过程。

## 7. 时间、范围与提交边界

### 明确不做

不要求分布式集群、eBPF/内核态、全流量存储与全文检索、生产级高可用或多租户。可参考或局部使用 **ELK**、**Wazuh**、**Grafana** 等，但界面与核心业务逻辑仍须自建。前端可以使用 UI 框架或模板，需注明来源。

### 环境与提交

- 自备机器，优先使用 Docker；Windows、Mac 的 Docker Desktop 均可。
- 附录中的 compose 片段和 pcap 生成脚本只是起点，可全部替换；原题面提示 compose 片段未验证，应以官方文档为准。
- 邮件标题：`[应届动手题] 姓名 - 学校/专业`。
- 邮件正文：仓库链接或 zip 网盘链接、录屏链接、自验报告 PDF、实际工时。

### 建议进度

| 时间 | 建议目标 |
|---|---|
| T+0–4h | 打通 pcap → **Suricata** → `eve.json` → 入库 → 页面显示 |
| T+4–12h | 采集与归一化、去重、告警列表/详情/总览 |
| T+12–20h | 自建数据、ground truth、自动评测 |
| T+20–28h | 变异测试、误报治理、规则打磨 |
| T+28–40h | 安全加固、文档、录屏 |
| T+40–48h | 处理风险并留出缓冲 |

题面建议第一天结束前就有可交互界面，哪怕只有一条演示数据；但最终检测效果必须由真实的自建数据验证。

## 8. 评分与通过条件

| 评分维度 | 分值 | 重点 |
|---|---:|---|
| 闭环可运行 | 20 | 干净机器一键启动；pcap 到界面不超过 5 分钟；无需手工改配置 |
| 检测有效性 | 20 | 场景覆盖、规则质量、TP/FP 可复算；规则不能只是照搬 ET Open |
| 数据自验方法论 | 15 | ground truth 严谨、可复现；含负样本、变异测试和诚实 FN 分析 |
| 工程质量 | 15 | 分层、错误处理、日志、外部配置、测试及无注入漏洞 |
| 界面与可用性 | 10 | 信息架构支持研判，不是简单堆表格 |
| Agent 协作 | 10 | 交互记录真实，能指出 AI 错误并形成验证闭环 |
| 答辩与代码理解 | 10 | 能解释任意代码、现场改需求并说明系统边界 |
| 加分 | 最多 +10 | 完成 4.3 中的 Could 项 |

- 通过线：总分至少 60，且“闭环可运行 / 检测有效性 / 答辩与代码理解”各自不低于该项满分的 50%。
- 直接淘汰：伪造数据或结果；无法解释提交的代码。
- README 无法启动且 10 分钟内修不好，扣 15 分；每缺一项交付物扣 3 分。

## 9. 题面 FAQ 摘要

- 可以用 Elasticsearch 或现成 SIEM 做存储和检索，但 Web 界面和检测业务逻辑要自建。
- 没有真实流量就自己生成；数据自验本身就是考点。
- SQLite 可以满足需求；选型合理比选型高级重要。
- 做不完很正常；按 MoSCoW 取舍，并说明砍掉什么、原因及多一天会先补什么。
- 可以让 Agent 写代码，但必须能回答随机代码段的设计原因。
- 无需 Suricata 商业版，开源版 7.x 足够；云主机可用，前提是能够复现。

## 10. 附录材料速查

原题面提供了可选的 compose 起点、一个正常 DNS/HTTP 示例 pcap 和一个 SYN 扫描示例 pcap 生成脚本，以及 `eve.json` 常用字段说明。它们是参考材料，不替代自建多场景数据集。字段重点包括：

- 通用事件：`timestamp`、`event_type`、`flow_id`、`community_id`。
- 五元组及协议：`src_ip`、`src_port`、`dest_ip`、`dest_port`、`proto`、`app_proto`。
- 告警字段：`alert.signature_id`、`alert.signature`、`alert.severity`、`alert.category`、`alert.payload_printable`。
- 流量统计：`flow.pkts_toserver`、`flow.bytes_toserver`。

Ground truth 示例结构及具体参考值请查看原题面附录 B；实现时应为每个 pcap 建立各自的 ground truth 文件。
