## 二、高优先级缺口（影响评分）

### 2.1 M4 告警列表“过滤 / 排序 / 分页”未真正满足（硬性要求）

需求 §4.1 明确要求告警列表“支持过滤、排序、分页”。现状：

- **过滤**：后端 `handleListAlerts`（`backend/internal/httpapi/data_handlers.go`）仅支持 `task_id / sid / src_ip` 三个参数，缺失时间、severity、协议、处置状态；前端 `Alerts.tsx` 无任何过滤控件。
- **排序**：后端 `queries/alerts.sql` 的 `ListAlerts` 硬编码 `ORDER BY ts DESC`，无排序参数与服务端白名单；前端表格列无 `sorter`。架构 §5.2 声明的“排序字段白名单”实际不存在。
- **分页**：前端 `Alerts.tsx` 只拉 `limit=100`，`Table` 的 `pagination={{ pageSize: 20, total }}` 仅在这 100 条内做**客户端**分页，翻页不请求服务端下一页，第 100 条之后告警界面永远看不到。

**影响**：M4 界面四件套中最实的一条，答辩现场演示易被当场挑出。

### 2.2 自验 FP 判定口径过宽，P=1.0 / FP=0 站不住（核心考察项 M5）

`validation/run_validation.py` 的 FP 判定：

```python
fps = [a for a in alerts if a["id"] not in matched_ids and a["sid"] not in exp_sids]
```

即：**只要告警 sid 出现在预期 sid 集合里，无论五元组/时间窗是否匹配，都不计 FP**。这比需求 §5.3 原文“攻击 pcap 中五元组、时间窗完全不匹配的告警即 FP”宽得多。后果：

- `web_attacks` 360 条告警只有 2 条预期，约 240 条五元组不匹配的告警被 sid 豁免；
- `dns_tunnel` 160 条、`ssh_bruteforce` 60 条、`scan_syn` 234 条同样有大量“sid 相同但五元组/时间窗不匹配”的告警被豁免（合计约 370+ 条）。

严格按 §5.3 口径，这些都应计入 FP，Precision 不会是 1.0。需求 §5.6 特别提醒“结果全绿会被复核”。此外 `web_attacks` 的 ground truth 描述“3 源 × 3 资产”却只列 2 条预期，ground truth 本身欠完整（§5.2 要求每条预期逐项枚举）。

**影响**：数据自验方法论（15 分）+ 诚实性红线，是当前最需主动、如实修正之处。

### 2.3 C1 实时推送“接口存在但端到端未接通”，实为轮询

核实结果（grep 确认）：

- 后端 `realtime.go` 定义了 `Publisher / PublishAlert / PublishGroup`，但**整个后端从未实例化 Publisher、从未调用任何 Publish 方法**；worker（`cmd/worker/main.go`）回放→采集→聚合→串联后不发布任何消息，api 也不发布。只有 `stream_handler.go` 的 SSE 端点在做订阅，等于一条永远收不到消息的通道。
- 前端全仓库**没有任何 `EventSource`、没有 `/api/v1/stream` 连接**：`Alerts.tsx` 用 `refetchInterval: 5000`、`Overview.tsx` 用 `refetchInterval: 8000` 轮询刷新。

**影响**：C1（SSE 实时推送）实际不具备实时能力，界面靠 5~8 秒轮询“伪实时”。README 把 C1 标为“已实现”不实。

### 2.4 审计与规则版本两张表是“死表”，与架构 §4.2/§6.6 相悖

迁移 `0001_init.sql` 建了 `audit_log` 和 `rule_revisions`，但全后端（grep 确认）**没有任何代码写入这两张表**：

- `handleToggleRule` 更新规则后既不写 `rule_revisions`（无版本快照）也不写 `audit_log`；
- `handleCreateRule` 同样不写；
- 只有 `handleTriageGroup` 写了 `triage_actions`（处置审计）。

架构 §4.2 第 2 步、§5.1、§6.6 承诺的“规则变更写版本与审计、登录/上传等敏感操作审计”未落地。同时 §7.2 规划的「审计日志」页面在前端不存在（`App.tsx` 无此路由），README 也未说明砍掉。

### 2.5 S6 引擎可观测大概率失效（stats 字段映射错误）

`eve.go` 的 `Stats` 结构字段与 Suricata 实际 `stats` 事件不匹配：

- `Detect.Alerts` json tag 为 `"alerts"`，Suricata 实际是 `detect.alert`（单数）→ 恒为 0；
- `KernelPackets.Dropped` 期望 `kernel_packets.dropped` 嵌套，实际是 `capture.kernel_drops` → 恒为 0；
- `RuleReload`（json `"rule_reload"`）不是加载耗时，stats 事件也无该顶层字段；
- `ingest.go` 调 `CreateEngineStat` 时未传 `RulesLoaded`，`rules_loaded` 列永远为 NULL。

结果：「引擎状态」页只能拿到 `agent.running` + `uptime`，丢包/规则加载耗时/吞吐几乎都是 0/NULL。README 把 S6 标为“已实现”，与实况不符。

### 2.6 D1“跨两天至少 10 次提交”未满足

`git log` 显示 21 次提交**全部集中在 2026-10-29 单日**（14:32:05–20:56:32，约 6.5 小时）。需求 §3 D1 要求“跨两天至少 10 次提交”，当前历史不满足“跨两天”。

### 7.3 「不像安全产品」的具体差距（对照竞品）

当前界面是「表格 + 卡片」的 CRUD 形态，缺乏安全研判产品的关键工作流。逐条对照：

1. **缺告警研判工作台 / 处置队列**（对标 EveBox Inbox、Security Onion Alerts）：无「待处置 / 已确认 / 误报」的队列视图与计数，无批量处置、无分配责任人、无研判注释；处置只散落在「聚合处置」页单条点链接。
2. **缺 MITRE ATT&CK 攻击链可视化**（对标 Security Onion / 阿里云 NDR 威胁图谱）：「攻击事件」页只有表格 + 文本 tag（`recon → bruteforce → …`），无图形化攻击链、无战术矩阵、无时间线。
3. **缺威胁情报与资产上下文**：告警详情只有五元组，无 IP 地理位置、无恶意情报标签、无资产指纹/分组，研判时无法判断「这个源 IP 是谁、是否已知恶意」。
4. **告警详情是「原始 JSON 堆叠」**：payload 无高亮、HTTP 请求/响应未结构化展示、关联 DNS/TLS 事件未聚合到详情，研判效率低。
5. **缺检索 / 猎杀（Hunt）**（对标 Security Onion Hunt、EveBox 查询）：只能按 `task_id/sid/src_ip` 三个字段过滤，无组合检索、无全文、无保存查询。
6. **缺案件管理（Cases）**：有自动事件串联（incidents），但无人工建案、跨事件合并、处置结论沉淀。
7. **总览仪表盘不可交互**：无时间范围选择器、无图表下钻（点「某签名」跳到该签名的告警列表）、无导出。
8. **缺导出/报告**：无告警 CSV/PDF 导出。
9. **无实时流**：见 §2.3，界面靠轮询。
10. **规则管理方向正确但缺来源/规则集管理**（对标 Scirius）：无批量启停、无规则来源分组、无规则命中统计回写。

> 已做对、值得保留的：全中文运营界面、结构化表单建规则（对标 Scirius 但更轻）、事件串联、ATT&CK 技术列、severity 配色。差距主要在「研判工作流、上下文情报、可视化与下钻」这三层。

| Alerts | 告警研判队列 | ⚠️ 有列表，无队列/批量/注释 |
| Dashboards | 可交互仪表盘 | ⚠️ 有静态总览，无时间选择/下钻/导出 |
| Hunt | 检索猎杀 | ❌ 无（仅 3 字段过滤） |
| Cases | 案件管理 | ❌ 无（仅自动事件串联） |
| Detections | 检测规则 | ✅ 有（列表 + 启停 + 表单创建） |
| PCAP | 取证 | ⚠️ 仅回传整段 pcap，未切片 |
| Attack Navigator | ATT&CK 矩阵 | ❌ 无（仅文本列） |
| Grid / Administration | 节点与配置管理 | ❌ 无 |

EveBox 关键能力佐证：**Inbox 待办队列**（告警管理）、**Event search**（事件检索）、**PCAP extract**（取证下载）——这三项恰是本项目当前最薄弱的三个环节。
